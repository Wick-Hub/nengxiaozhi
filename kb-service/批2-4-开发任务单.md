### 任务 2.4 延伸 · 接入 campus-ai-gateway（C-01 LLM 网关）✅ 已完成

> **结论：配置级接入，`LLMClient` 一行不用改。** 以下是实现记录。

> - **先做的是代码级核对**（读源码而非 README）：数据面是 17 行透明反代
>   （`FlushInterval=-1` + `X-Accel-Buffering: no`）；响应体原样透传；请求体只读
>   `model`/`stream`/`max_tokens` 做白名单与 TPM 预占，其余字段原样转发；
>   错误体 `{"error":{"code","message","request_id"}}` 与 OpenAI 同构。
>   → 所以接入是改配置，不是改代码。
> - **顺带的架构收益**：网关 `authMiddleware` 删掉客户端 `Authorization` 再由数据面替换为
>   ThinkWatch Key → **厂商 API Key 不需要交给能小智**。
> - **修掉接入后会立刻暴露的真实缺陷**：`pipeline` 不捕获 `LLMError`，
>   非流式 `/api/chat` **完全没有 try/except** → 网关 403（白名单不匹配）会冒泡成 500，
>   用户只看到「Internal Server Error」，无任何可定位信息。流式虽有捕获但只传 `str(exc)` 一坨。
> - **改法**：
>   ① `LLMError` 结构化 —— 新增 `status_code`/`code`/`request_id`/`model_code` 与
>   `to_dict()`/`hint`；`parse_upstream_error()` 兼容网关与 OpenAI 两种错误体，
>   **非 JSON 响应保留原文**便于排查；`requestId` 在错误体缺失时**由响应头 `X-Request-Id` 兜底**；
>   ② `/api/chat` → **502 + `errorDetail`**；**刻意不透传上游状态码**（网关的 401/403 说的是
>   「网关不认我们这把 Key」，对前端而言不是「需要登录」，透传会把前端引到错误方向），
>   真实状态码放在 `errorDetail.status`；
>   ③ `/api/chat/stream` 的 `error` 事件追加 `errorDetail`（`error` 字段保持字符串，契约不破）；
>   ④ `model_admin.probe_model` 失败时回 `code`/`status`/`requestId`/`hint`；
>   ⑤ `static/model.js` 自测结果显示「处置建议」与 `requestId`。
> - **`ApiResult` 只加字段不改字段**：新增 `errorDetail`（可为 None），老前端读 `error` 不受影响。
> - **验收**：
>   `tools/verify_gateway.py`（静态 5 组 + 在线 11 断言 + `--self-test` 假端点自测）、
>   `tools/_fake_gateway.py`（按网关契约实现的假端点）、
>   `tests/test_gateway_integration.py`（**11 项**：默认路径与库内模型两条成功链路、
>   403/401/连接失败**三条失败链路都必须 502 而非 500**、流式 delta/done/error 三态、
>   契约键集合守卫）。实测 `--self-test` **13 PASS / 0 FAIL**。
> - **变异测试验牙**：把 `/api/chat` 的 `except LLMError` 改回 `raise`（即退回修复前行为），
>   3 个用例立刻 FAIL；还原后 11 passed。
> - **实测状态（2026-10-19 更新）**：已在真实网关完成端到端验证

### 批2 补测试与回归（2.1 / 2.2 / 2.4 的数据层兜底）

> **动因**：本机（及多数开发机）没有 MySQL，`tests/test_mysql_store.py` 整体跳过，
> 于是 2.1/2.2/2.4 新增的 **MySQL 专属代码路径**长期处于「写了但从未执行过」的状态：
> `_row_to_dict` 的归一化、`_load_mysql` 的筛选下推、`_payload` 的 NULL 语义。
> 这些路径一旦写错，JSON 模式下所有测试都会通过 —— 属于**测试盲区**，不是「覆盖率不足」。

> **做法**：`tests/test_store_mysql_stub.py`（**32 项**）+ `tools/verify_mysql_branch.py`
> （**41 PASS**）用**场景驱动的假连接**替换真实 SQL：按调用顺序发牌返回结果集，
> 并留存语句供断言。四组检查：
>
> 1. **归一化同形**：同一份逻辑记录分别经 JSON 后端写入回读、经 MySQL 行归一，
>    **对外 dict 键集合必须完全一致**（否则前端要为两种后端写两套解析逻辑）；
> 2. **可辨识 NULL**：显式 `temperature=0.0` 原样落库（0.0 是合法温度，不是哨兵值）、
>    未配置的 `top_p`/`max_tokens` 落 NULL；改 `.env` 默认值后未配置助手仍为 `None`；
> 3. **筛选下推**：会话级筛选（role/agent/channel）与时间范围必须出现在 SQL 里
>    （用 `literal_binds` 编译后比对），扫到无筛选时不产生多余 `WHERE`；
> 4. **Key 只进不出**：列表/详情默认不解密、掩码恒为 `****`（不泄露长度）、
>    落库为密文且明文不出现在 SQL 参数里、三态更新（不动 / 清空 / 覆盖）。
>
> **额外产出**：
> - MySQL 分支**不得回退读 JSON** 显式断言（否则「双后端语义一致」是假的）；
> - 断言工具已具备**牙齿**：人为注释掉 `chatlog_admin` 的 role 下推、把 `agent_store`
>   的 `temperature` 归一改成物化默认值，3 个用例立刻失败（变异测试后已还原）。
>
> **边界（如实声明）**：这是**模式分支验收**，不是实机验收 —— MySQL 语法、类型映射、
> 字符集、事务语义仍须在有库环境跑 `pytest tests/test_mysql_store.py` 与
> `verify_*.py --store mysql`。
>
> **顺手纠正的陈旧数字**：`verify_chatlog_ui.py` 在 README 记 29、任务单记 28、
> 总计划表记 30 —— 实跑为 **30**，三处已统一。
